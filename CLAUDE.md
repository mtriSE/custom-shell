# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A POSIX-style shell in C++23, written from scratch. Docs, comments and commit messages are written in English.

## Commands

- Build + run: `./run.sh` (cmake configure + build, then execs `build/shell`).
- Rebuild only: `cmake --build build`
- Unit tests (Catch2 v3, `tests/unit/`): `cmake --build build --target unit_tests && build/unit_tests`; `tests/run.sh` builds and runs them, and fails if they are not configured. Catch2 is only for the tests: `sudo apt install catch2` (Fedora `catch-devel`, Arch `catch2`), or configure with `-DSHELL_FETCH_CATCH2=ON` (needs network; do not do this without asking the user). The sources are built as the static library `shell_core` (everything but `main.cpp`) plus `shell`.
- Terminal tests: `tests/pty/run.sh` (needs `build/shell` and `python3`; runs the shell on a pty). `tests/run.sh` runs them after the golden cases.
- Regression tests: `tests/run.sh` (needs a built `build/shell`). Each `tests/cases/<name>.in` is piped to the shell on stdin, stdout+stderr are diffed against `<name>.out`, in a scratch temp dir (the pid of a `[N] pid` line is normalised to `PID` first). `tests/run.sh --update` rewrites all `.out` files — review the git diff afterwards. To run one case, copy it to a temp dir and run `build/shell < case.in` manually (the script has no filter).

Prerequisites (install before the first build): CMake >= 3.13, a C++23 compiler (GCC 13+ / Clang 17+ recommended) and the GNU readline *development* package. Debian/Ubuntu: `sudo apt install build-essential cmake libreadline-dev`; Fedora/RHEL: `sudo dnf install gcc-c++ cmake readline-devel`; Arch: `sudo pacman -S --needed base-devel cmake readline`; `python3` (standard library only) for the terminal tests in `tests/pty/`; Catch2 v3 for the unit tests only (not for building the shell); the full list (openSUSE, Alpine, Void, Gentoo, Nix) is in README.md. A build error `readline/readline.h: No such file or directory` means the dev package is missing; do not work around it, install it (ask the user to run it, since it needs sudo).

`CMakeLists.txt` globs `src/*.cpp` and `src/*.hpp` recursively, so new files are picked up after re-running cmake. It links `readline`, which provides line editing and TAB completion when stdin is a terminal.

## Architecture

`main` → `Shell::run()` (`shell.cpp`) is a read-parse-expand-execute loop that carries `last_status_` (for `$?`) between lines.

- `read_line` (`shell.cpp`): uses `readline("$ ")` when stdin is a tty, otherwise prints the prompt and uses `std::getline`. The split is deliberate: readline echoes input on non-tty stdin, which would break `tests/run.sh`, so TAB completion can't be tested there (drive the binary through a pty instead).
- `signals.cpp`: when stdin is a tty, SIGINT is caught (the handler writes a byte to a non-blocking pipe, `interrupt_fd()`), SIGQUIT is caught by a no-op, SIGTSTP, SIGTTIN and SIGTTOU are ignored in the shell (children reset all five with `reset_child_signals()`). No project or readline dependency. `completion.cpp` `init_readline` sets `rl_catch_signals = 0` and `rl_getc_function` to a reader that polls stdin and that pipe: Ctrl-C at the prompt clears the line (after ESC/Ctrl-X or in Ctrl-R the reader first returns Ctrl-G so readline drops that state, then the `'\n'`), `prompt_was_interrupted()` tells `Shell::run`, which sets `$?` to 130 and skips the line. For foreground jobs `wait_foreground` reports death by SIGINT/SIGQUIT in `Outcome::interrupted` (waits retry on `EINTR`), and `Shell::run`'s `notify` callback then prints one newline when interactive.
- `job_control.cpp` (job control, only when stdin is a tty): `init_job_control()` makes the shell its own process group and the terminal's foreground group and saves the terminal modes. Every external command or pipeline is a job in its own process group. `wait_foreground(job)` hands the terminal to the job's group (`tcsetpgrp`, via the RAII `TerminalHandoff`), waits with `waitpid(-pgid, WUNTRACED)` until the job is `Done` or `Stopped`, takes the terminal back and restores the shell's modes; a stop saves the job's modes in `Job::modes`. `resume(job, foreground)` is `SIGCONT` (plus the job's modes and the terminal for `fg`). Ctrl-Z leaves the job `Stopped` in the table, `$?` is 148, and `Shell::run`'s `notify` callback prints the `[N]+  Stopped ...` line after redirects are undone (`Outcome::stopped_job`).
- `completion.cpp`: `rl_attempted_completion_function` hook. In command position (no words before the cursor) it completes builtin names (`builtin_names()` in `builtins.cpp`) plus executables in `$PATH` (`executables_in_path()` in `path_utils.cpp`, rescanned on every TAB, unreadable dirs skipped), deduplicated, with `rl_attempted_completion_over = 1` to block readline's filename fallback. For arguments, if the line's first word has a script registered via `complete -C` (`find_completer()`), the script is run (`capture_lines()`, no timeout, but Ctrl-C kills the script's own process group and drops that completion; the line stays as typed) as `script <command> <word being completed> <previous word>`, with `COMP_LINE` (whole line) and `COMP_POINT` (cursor byte offset) set in the child only, and each stdout line is a candidate, again without filename fallback. Otherwise the hook returns `nullptr`, so readline's built-in filename completion runs (for any command, nested paths and directories included). With several matches the first TAB rings the bell and the second lists them via `display_matches` (one line, two spaces apart; readline sorts and dedupes). Both sources fill the file-scope `candidates`, which one `candidate_generator` hands to readline.
- `parser.cpp`: single-pass state machine (Normal / SingleQuote / DoubleQuote) that turns one line into a `PipelineNode`: `stages` of `ParsedCommand` (`words` + ordered `ParsedRedirect`s). `parse_line` returns a `Node`: a `PipelineNode`, an `AndOrNode` (pipelines joined by `&&`/`||`, `connectors.size() == pipelines.size() - 1`), or a `ListNode` (items separated by `;`, each a `PipelineNode` or an `AndOrNode`; a trailing `;` is dropped and a single item is never wrapped); a `Grouper` walks the tokens once, left to right, so the first syntax error by position is the one reported (`;` at the start or after `;`/`|`/`&&`/`||` is an error near `;`, `;;` is always an error near `;;`, `&&`/`||` at the start or after an operator is an error near that operator, at the end of the line near `newline`). Every `PipelineNode` keeps its source `text` (the text of its job). Subshells and `if` will be added as alternatives. It expands nothing: a `Word` (`word.hpp`) is a list of pieces, each with its `Quoting`. Handles quoting, backslash escapes, redirect operators (`>`, `>>`, `N>`, `>&N`), an unquoted `|` that splits the line into stages, and a trailing unquoted `&` word (`PipelineNode::background`). An empty stage is a syntax error. Syntax errors return `nullopt` plus a message, and the shell sets status 2.
- `expansion.cpp`: `expand_word` (`$?`, replaced in unquoted and double-quoted pieces, and `~`/`~/path` at the start of an unquoted word, replaced by `HOME`; `~user`, `~+`, `~-` and tilde after `=` or `:` stay literal) and `expand_pipeline`, which turns a `PipelineNode` into the `Pipeline` of final text (`command.hpp`) that `run_pipeline` executes, and checks the `>&` target (`x: Bad fd number`, `10: Bad file descriptor`; status 2, nothing has run). It takes `last_status` and `HOME` as values (`ExpansionContext`); only `context_from_environment` reads the environment. A line with two errors reports the syntax error first.
- `evaluator.cpp` `evaluate(node, step)` is the order of evaluation and nothing else: a list runs every item, a chain runs its next pipeline only if the connector says so by the status of the last one that ran (a skipped one leaves it alone), stops at `exit` or an interruption (a stopped job, status 148, does not stop it), and returns only `exit`, `status`, `interrupted`. The pipeline runner is the `StepFn` hook, so `tests/unit/evaluator_test.cpp` uses a scripted step.
- `runner.cpp` `run_tree` builds the real step (keeping `$?` up to date per command) and calls `evaluate`; for each pipeline the step calls `expand_pipeline` right before the pipeline runs (with `parsed.text`, the pipeline as typed, as the text of its job) (an expansion error is printed, status 2, nothing runs), then `run_pipeline`, then the `Notify` callback that `Shell::run` passes (`[N] pid`, the `Stopped` line, the newline after Ctrl-C and the refusal of `exit` with stopped jobs happen there, after each pipeline once its redirects are undone). `Outcome` lives in `outcome.hpp`.
- `runner.cpp` `run_pipeline` (the execution half, split from `shell.cpp`; `Outcome` is in `runner.hpp`): one stage runs as before; several stages are forked together (`run_stages`), each wired to the neighbouring `pipe()` ends by `dup2` before its own redirects, all pipe fds closed in the children and in the parent (or readers never see EOF), then the parent waits for all (as one job in one process group, see `job_control.cpp`) and takes the last stage's status. Builtins in a stage run in the child (`fg`/`bg` there print `no job control`). `a | b &` is one background job (registered in the table, `[N] pid` with the last stage's pid, not waited for).
- `runner.cpp` `run_command`: applies redirects *first*, then dispatches builtin → external (via PATH) → "command not found" (127). Applying redirects before dispatch is what makes them work uniformly for all three.
- `redirect.cpp` `FdRedirect`: RAII wrapper that `dup2`s a real file descriptor and restores it on destruction. Redirection works at the fd level (not by swapping stream buffers), so builtins writing to `std::cout`/`std::cerr` and forked children both follow it. `RedirectStack` in `runner.cpp` holds them and must unwind in reverse order, because multiple redirects on the same fd each saved the previous state. Saved fd copies live at fd 10 and up, so the parser caps user fds at 9 (`MAX_FD`).
- `builtins.cpp`: table of `exit`, `echo`, `type`, `complete`, `jobs`, `fg`, `bg`, `pwd` (prints `std::filesystem::current_path()`), `cd` (a plain `chdir`, with the error text from `errno`; it receives final text (a `~` was already expanded by `expansion.cpp`); bare `cd` uses `$HOME`, or tries the literal `~` if it is unset; it runs in the shell process so the cwd really changes, except inside a multi-stage pipeline where it runs in a child). `jobs` lists the jobs in `job_table.cpp` in the bash format `[1]+  Running                 sleep 10 &` (`Running`, `Stopped`, `Done`; ` &` only on running background jobs); `print_jobs()` first refreshes the processes' states with a non-blocking `waitpid` (with `WUNTRACED`/`WCONTINUED` on a terminal), shows finished jobs once as `Done` and drops them from the table; `exit` or Ctrl-D with a Stopped job is refused once (`There are stopped jobs.`, `$?` 1; `Shell::exit_refused_`), the next attempt sends SIGHUP+SIGCONT to Stopped jobs (`end_stopped_jobs()`) and leaves; running background jobs are left alone. `Shell::run` also calls `print_jobs` with `only_news` before every prompt: it then prints only `Done` jobs and background jobs that have just stopped (a `cat &` stopped by SIGTTIN), once each. `+` is the most recently stopped job (else the most recently backgrounded one), `-` the next. `fg` and `bg` continue a job in the foreground or background; job specs (`%%`, `%+`, `%-`, `%N`, `N`) are resolved by `resolve_job()`, and with piped input or inside a pipeline stage they print `fg: no job control`. `complete -C <script> <command>` stores the script in `completer_registry.cpp` (the args are already whitespace-split by the parser); `complete -p` reprints specs from there as `complete -C '<script>' <command>`, or reports "no completion specification"; `complete -r [command...]` removes them (all of them without names), silently. `type` uses `path_utils.cpp` (`find_in_path`) for PATH lookup, which `shell.cpp` also uses.
- `executor.cpp`: `start_process()` forks and execs the resolved executable and returns its pid without waiting (`pgid` 0 = a new process group, a pid = join it, -1 = none; `setpgid` in both child and parent). `exec_replace()` is the exec-in-place used by pipeline stages. Background single commands are registered by `Shell::run` (`announce_job`: `add_job` with the line as typed, printing `[N] pid` after the command's redirects are undone); they are reaped by `print_jobs()`. `capture_lines()` does the same with stdout piped back and returns the output lines (used for completer scripts).

`main.cpp` sets `std::unitbuf` on cout/cerr so output is flushed before a child process writes, keeping ordering correct.
